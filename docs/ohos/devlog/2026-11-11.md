# 2026-11-11 · 在真机 demo 上撞 bin 的签名

## 读到的（改变了计划）

[应用程序包集成 bin 文件（PC/2in1）](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/hap-bin)
——**从 API 24 起，HAP 官方支持集成 ELF 可执行文件**，不需要 HNP：

| 项 | 做法 |
|---|---|
| 放哪 | `entry/libs/{abi}/EXAMPLE`（和 .so 同一个目录） |
| 声明 | `module.json5` 的 `executableBinaryPaths: [{ path: "libs/arm64-v8a/EXAMPLE" }]` |
| 打包 | `extractNativeLibs: true`（安装时解压）+ build-profile 的 `collectAllLibs: true` |
| 权限 | ELF 的 `.permission` 节（JSON），可用 `objcopy --add-section` 或 `binary-sign-tool -moduleFile` 写入 |
| 继承 | 声明 `ohos.permission.INHERIT_PARENT_PERMISSION` 可继承父进程的 system_grant 权限 |
| 装到 | `/data/app/el1/bundle/public/<bundleName>` |

**这比 HNP 省一整层**：不用 `hnpcli`、不用 `hnpPackages`、不用独立签名，随 HAP 安装。
所以设计里"HNP 里的 ELF"改成"libs 里的 bin"，TODO 已同步。

## 在 demo 上做的实验

用 `/storage/Users/currentUser/Workspace/demo`（已装的真机 HAP，有签名材料）验证。

1. 写了个纯 Go 的探针（`/storage/Users/currentUser/Workspace/ohos-probe`）：

   ```sh
   CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags="-s -w" -o mygo-probe .
   # ELF executable, 64-bit LSB arm64, static —— 1.7MB
   ```

   在这台机器上直接跑得起来（`MYGO_PROBE_OK pid=...`），说明 Go 的二进制和这个内核没问题。

2. 按文档接线：`libs/arm64-v8a/mygo-probe` + `executableBinaryPaths` + `extractNativeLibs` + `collectAllLibs`，
   并在 `napi_init.cpp` 的 `Init()` 里加了个 `runBinProbe()`（fork + execve + 抓 stdout，复用 demo 现成的
   `runElfExecTest`）。

3. **bin 确实进了 HAP**：

   ```
   $ unzip -l entry-default-signed.hap | grep mygo-probe
    1778928  libs/arm64-v8a/mygo-probe
   ```

4. **装不上**：

   ```
   $ hdc install -r entry-default-signed.hap
   msg:error: failed to install bundle. code:9568393 error: verify code signature failed.
   ```

5. 试着自签名（SDK 自带 `toolchains/lib/binary-sign-tool`）：

   ```
   $ binary-sign-tool sign -inFile mygo-probe -outFile signed -selfSign 1
   write code sign data success
   $ binary-sign-tool display-sign -inFile signed
   permission is not found
   code signature is self-sign
   ```

   重新打包安装——**还是同样的错**。

6. 做了隔离实验：把 ELF 从 `libs/` 和 `executableBinaryPaths` 里拿掉，其余配置不动，重新打包
   —— **装成功**。

**当时的结论：拦人的是 ELF 自己的代码签名，自签名不被接受。**（后半天被推翻了一半，见下节。）

## 这意味着什么

1. **构建多一步，而且是必须的**：`mygo build -platform ohos/arm64` 要在打包前用
   `binary-sign-tool sign -appCertFile <cer> -keystoreFile <p12> -keyAlias <alias> -signAlg SHA256withECDSA`
   签引擎 ELF，**用应用自己的证书**。
2. **密码要能拿到**。DevEco 把 keystore 口令加密写在 `build-profile.json5`（`0000002025...`），
   `binary-sign-tool` 只吃明文。所以要么在 `mygo.config.ts` 里放一条"签名材料"配置、由 CLI 驱动
   `hap-sign-tool`，要么走环境变量。**这是 D⁺ 目前唯一没有答案的一步。**
3. **引擎与应用签名绑定**：同一个 Go 引擎换一个应用就得重签，不能"一次构建到处塞"。

## 第二轮：签名的真相（当天稍后）

第一轮的结论"必须用应用证书签"只对了一半。完整轨迹：

| # | ELF | HAP 签名 | 结果 |
|---|---|---|---|
| 1 | 未签 | hvigor | `9568393 verify code signature failed` |
| 2 | 自签名 | hvigor | 同上 |
| 3 | 应用证书签（hda 的 key，链已验） | hvigor | 同上 |
| 4 | 应用证书签 | hda 重签（临时证书） | 同上 |
| 5 | 应用证书签 | hvigor + **声明 `ALLOW_EXTERNAL_NATIVE_CODE`** | **`9568289 grant request permissions failed`** ← 签名检查过了 |
| 6 | 应用证书签 | hap-sign-tool + 带 ACL 的 profile | `9568393`（我手工签的 HAP 本身不合法） |

由此确定：

1. **真正的闸门是权限**：`ohos.permission.ALLOW_EXTERNAL_NATIVE_CODE` 必须在
   `module.json5` 里声明（第 5 步才让签名检查放行）。
2. 它是**受限权限**，必须在 Provision Profile 的 ACL 里，否则第 5 步那样报
   "grant request permissions failed"。`hda profile --bundle-name ... --cert-id ... --acl ohos.permission.ALLOW_EXTERNAL_NATIVE_CODE`
   确实能生成带 ACL 的 p7b（已验证 p7b 里有这个字符串）。
3. 剩下的问题变成**用什么签 HAP**：第 6 步说明手搓 `hap-sign-tool` 参数不对。
   正路是让 **hvigor 用同一套材料（hda 的 key + 带 ACL 的 profile）签**——
   把 `build-profile.json5` 的 `signingConfigs[].material` 指向 hda 的 p12/cer/p7b。
   麻烦在于 hvigor 期待 DevEco 加密格式的口令，而 `bash` 侧只有明文。

**下一步只有一条**：换签名材料重建一次。成了，才有机会问"应用进程能否 execve 这个 bin"。



## 第三轮：安装器自己说了原因

按 -signCode 1 重签（hap-sign-tool 接受该参数，verify-app 通过，ELF 也在 code sign block 里），
安装仍失败，但日志把原因写出来了：

```
E C05A06/installs/CODE_SIGN: CheckCertHasBinaryCertExtension: Binary cert extension not found in certificate
E C05A06/installs/CODE_SIGN: [ParseNativeLibSignInfo]:Libs signature not found: signMap_ size:4, signMapPreSize:1
E C01122/installs/BMSInstalld: installd_host_impl.cpp:VerifyCodeSignatureForHap:2523 hap or hsp code signature failed due to -3
```

两件事：

1. **证书缺 Binary cert extension**：ELF 的代码签名要一张**二进制证书**（AGC 单独申请，
   binary-sign-tool 文档里"申请二进制证书"那一节），应用调试证书没有这个扩展。
   自签、应用证书签都失败，根因在这里。
2. `signMap_ size:4, signMapPreSize:1`：HAP 里 4 个 lib 只有 1 个有签名条目——
   签名块要覆盖 `libs/` 下每一个二进制，只签 mygo-probe 不够。

**结论：没有二进制证书就跑不通 bin**，与 HAP 由谁签（hvigor / hda / hap-sign-tool）无关。
hda 拿的是应用调试证书，帮不到这一步。



## 第四轮：HNP 也撞在同一处

按"只能走 HNP"的结论试了一遍：

1. 造 HNP：`mygo_1.0.0/bin/mygo-probe` + `hnp_1.0.0/hnp.json`（`{"type":"hnp-config","name":"mygo","version":"1.0.0","install":{"links":[...]}}`）
   → 第一次装报 `hnp_json.c:154 hnp cfg file not found`，补上 hnp.json 后进入下一步；
2. 注入 HAP（`zip` 追加 `hnp/arm64-v8a/mygo.hnp`）并用 hda 的证书 + `profile` 重签；
3. 安装：`9568407 Failed to install the HAP because installing the native package failed`。

原因还是签名：

    E C05A06/hnp/CODE_SIGN: [ParseNativeLibSignInfo]:Libs signature not found: signMap_ size:0, signMapPreSize:0
    E installd: ProcessBundleInstallNative: Native package installation failed with error code: 8393475

HNP 的 `bin/` 也要逐个文件有代码签名，和 `libs/` 一模一样的检查。
加 `independentSign: true` 也一样（同样 9568407）。

直接 `bm install -p mygo.hnp` 也不行：`9568269 install file path invalid`——hnp 不归 bm 管。

**所以：HNP 不是绕过二进制证书的路，它只是换个位置放同一个二进制。**
zcode 的 electron.hnp 能跑，是因为那份 HNP 由华为用二进制证书签过，不是第三方自签能复制的。

## 结论（当天最终）

| 路线 | 是否要二进制证书 | 现状 |
|---|---|---|
| D⁺（libs/bin） | 要 | 阻塞 |
| D⁺（HNP） | 要 | 阻塞 |
| C′（进程内 cgo，只有 .so） | **不要**（.so 随 HAP 签名，无逐文件检查） | 唯一可行 |
| A（ArkWeb + wasm） | 不要 | 已被"不要 web"排除 |

## 第七轮：内存共享通了

在 demo 里加了一个 MEMSHARE 探针：应用进程（native）建 640×480 的缓冲区，把 fd 用 SCM_RIGHTS
发给 HNP 里的 Go 引擎，引擎 mmap 后写图案并回 ack，应用再读回校验。

    MEMSHARE sent=16 sendErrno=0 ack=1 bad=0 exit=0

- sent=16：16 字节几何头 + fd 一次 sendmsg 送出去，无错；
- ack=1：引擎收到、mmap 成功、画完、回了 ack；
- bad=0：应用读回的每个采样点都是引擎写进去的图案；
- exit=0：子进程正常退出。

**跨进程 fd + mmap 这条路在真机上成立**，而且是在应用沙箱与 HNP 进程之间、由应用自己 fork/exec 的。
之前的 ohos-frame spike 只在同一台机器上验证了协议；这次验证的是手机/PC 上真实的两个进程、
不同的 mount namespace。

剩下的是把「普通文件 fd」换成「图形 buffer 的 fd」（OHNativeWindow RequestBuffer 拿到的那个），
差别在 stride/usage/缓存，以及必须 SET_USAGE 带 CPU_WRITE。

## 第九轮（01:42–02:06）：S1 闭环 + S1.5 探针

### 协议换成了带类型的帧

原来的 16 字节头 + 1 字节 ack 只够证明"能动"。换成设计文档 §3 的形状：

    u8 kind | u32 len | payload
      1 FRAME  {u32 seq, u32 id, u32 w, u32 h, u32 stride, u32 size} + fd
      2 READY  {u32 seq, u32 n, n × {i32 x, i32 y, u32 w, u32 h}}   ← 左上原点
      3 QUIT

宿主把 rect 翻成左下原点（`y' = h - (y + hh)`）后交给 `FlushBuffer` 的 `Region`；
`n == 0` 表示整块。一帧一个 fd，引擎 mmap 一次就按 buffer 留住映射。

### 一个只有真跑起来才会发现的点：damage 是**按 buffer**的

窗口的 buffer 是环状的（这里是 4 块）。第 N 帧画进 A，第 N+1 帧进 B，第 N+4 帧才回 A——
**A 里躺着的是四帧前的内容**。所以"相对上一帧的脏区"这个说法在环里不成立：
每个 buffer 都要记住自己上次画到哪，第一次拿到某个 buffer 必须画满。

实测确认了这个必要性：一开始图省事按"全局上一帧"算，横带的残影在环上留了四条。
现在 `surface.bandTop` 挂在每个 buffer 上。

对应到框架：`platform.DamageSurface.PresentDamage` 的契约是"相对上一次 present"，
而 **ring 会把这个契约打断**。D⁺ 的宿主必须替 `ui` 兜住这一层——
哪个 buffer 第一次用，就得当整帧 flush：

    frames=780 damaged=776 whole=4 rects=2   ← whole 只有 4，就是环里四块的首帧

### 实测数字（2090×1324，2in1）

    mygo-host: frames=780 damaged=776 whole=4 rects=2 vsyncMisses=0
    engine: 780 frames, 776 damaged  interval p50=8.4ms p90=9.6ms p99=27.9ms

面板是 120Hz，`OH_NativeVSync` 一对一地把帧压到 8.33ms 的节拍上，
p50 就落在 8.3–8.6ms；p99 偶尔翻到 20–28ms，是漏了一次刷新——现在每帧只有一次
10 MB 级别的整屏 memset，等换成 `ui` 的 damage 光栅再看。

### 一起做完的

- **resize**：窗口拉开的动画里 `onSurfaceChanged` 会连发十几次（1910→1998），
  每次都 `SET_BUFFER_GEOMETRY rc=0`，画面跟着变。按文档说的 33ms 去抖还没加，
  现在靠"循环顶部、手上没有 buffer 时"改几何，够用。
- **看门狗**：`poll` 100ms 等不到 READY 就 `AbortBuffer` 并交给重启。
- **重启退避**：100/500/2000ms，三次放弃。这条被实测撞上过——HNP 没装好时
  引擎 execve 失败，日志正好把退避序列打全了。
- **PR_SET_PDEATHSIG(SIGKILL)**：应用被杀，引擎跟着走，不留孤儿。
- **引擎的 stdout/stderr 接进 hilog**：一条 `pipe` + 一个读线程。
  这一条是最值的一小时——引擎第一句报错就是靠它才看见的
  （`execve ... failed: Permission denied (errno 13)`）。

### S1.5 探针：三个问题，两个解决了一个问错了

引擎加了 `--probe`，宿主在 attach 时跑一次，输出走同一条 pipe：

    probe: purego ok getpid=10369 want=10369
    probe: drawing fail no OH_Drawing_CreateFont: Symbol not found
    probe: fonts ok 263 files: DejaVuMathTeXGyre.ttf,FTAeroSans-Regular.ttf,...

1. **purego 在 OHOS 的 musl 上能用。** `dlopen`/`RegisterLibFunc` 调用 libc 的
   `getpid`，返回值与本进程一致。这是 D⁺ 里最悬的一条，现在落地了。
2. **`/system/fonts` 从应用沙箱里读得到，263 个字体。** S3 不需要自带字体。
3. **`libnative_drawing.so` 存在，也能 `dlopen`，但我猜的函数名是错的。**
   `OH_Drawing_CreateFont` 不存在（`dlsym` 失败），所以这一条"fail"是我的探针
   写错了，不是库没有。NDK 里真正的文字 API 是整套 typography：

       OH_Drawing_CreateFontCollection / CreateSharedFontCollection
       OH_Drawing_CreateTypographyHandler / TypographyCreate
       OH_Drawing_TypographyHandlerAddText / PushTextStyle
       OH_Drawing_TypographyLayout / TypographyGetHeight / TypographyPaint

## 第十轮（02:20–02:30）：HNP 的权限位，与 S2 的骨架

### HNP 就是带权限的 zip

上一轮我把 chmod 不生效当成"工作区文件系统的坑"，绕道 `/tmp` 打包。
这是错的思路：**权限位本来就该由打包工具写进 zip 的中央目录**，
和打包机的文件系统没有任何关系。

`tools/hnp/main.go`：用 `archive/zip` 的 `FileHeader.SetMode`，
一条 `mygo_<version>/bin/mygo-engine` 记 0755，`hnp.json` 记 0644，
每次都从零写一个 zip（有旧版本的 zip 不是合法的包）。

    $ go run ./tools/hnp -version 1.0.6 -bin experiments/ohos-engine/mygo-engine \
          -target mygo-engine -out ohos/entry/hnp/arm64-v8a/mygo.hnp

装上去、跑起来：`engine pid=25169 size=2788248`，帧继续。
注意这是直接从工作区打包的，没有经过任何 chmod 生效的目录。

hda 那一侧读的也是这个字段（`hap_meta.cpp:492`）：

    file.mode = (attr >> 16) & 0777;

也就是 zip 中央目录 external attributes 的高 16 位。工具写对了，安装器就读对了。

## 第十一轮（08:19–08:30）：`ui` 在设备上画出了第一帧

### 帧的方向反过来了

S1 是宿主推着引擎走：无条件 `RequestBuffer` → 传 fd → 等 ack → `FlushBuffer`。
S2 起由引擎决定什么时候画：

    ui 要一帧 → REQUEST ────────────────▶ 宿主
                ◀──────────── FRAME {seq,id,w,h,stride,size} + fd
                ui 渲染 → PresentDamage 把脏矩形拷进那块内存
              PRESENT {seq, n, rects} ──▶ 宿主 → FlushBuffer(region)

宿主只在收到 `REQUEST` 时才 `RequestBuffer`，空闲时一帧都不发。

### 引擎就是框架自己的例子

没有新写应用：`examples/counter-native`（640 行的 counter，按键会变数字）直接编成引擎。

    GOOS=linux GOARCH=arm64 CGO_ENABLED=0 \
      go build -tags mygo_ohos -trimpath -o mygo-engine ./examples/counter-native

12.2 MB。跑起来是 `ohos` 后端，不是 Linux 后端。

### 三个坑

**1. `App.Run must be called from the main goroutine`**

`isMainThread()` 是 `backend().IsMainThread()`，而我把它实现成
`syscall.Gettid() == b.tid`，`b.tid` 在 `Init` 里赋值——可 `Init` 是 `Run` 内部才调的，
检查发生在调用 `Init` 之前，于是 `b.tid` 还是 0，恒假。引擎每次启动就退出，
宿主的重启退避把 100/500/2000ms 走了一遍，正好又验了一次。

改成包级的 `var mainTID = syscall.Gettid()`：包初始化器和 `main` 都跑在进程的主线程上，
而 `Run` 会 `LockOSThread` 把自己钉在那。

**2. 首帧的尺寸会抢跑**

`ui` 第一次布局就要 `Surface.Size()`，而尺寸原本靠 `SURFACE` 消息送——第一个尺寸
请求可能早于第一条消息。现在尺寸和缩放写在启动参数里（`--size=2090x1324 --scale=1.900`），
消息只负责之后的 resize。

缩放由 ArkTS 侧给：`display.getDefaultDisplaySync().densityPixels`，这台是 **1.90**。

**3. 又是 hvigor 的 mtime**

改 `host.cpp` 之后 hvigor 认为 native 任务是 up-to-date，装上去的还是旧 `.so`
（症状：NAPI 新函数 `undefined`）。必须 `rm -rf entry/.cxx entry/build`。
这条上一轮记过一次，这轮又踩到了——说明它不是偶发，是这个工作区文件系统的通病。

### 证据

    mygo-host: attach sid=... 2090x1324 scale=1.90
    mygo-host: engine pid=41235 size=12348312
    mygo-host: surface 2090x1324 rc=0 scale=1.90
    mygo-host: frames=1 damaged=0 whole=1 rects=0

链路是：`ui` 请求 → 宿主给 buffer（含 fd）→ `ui` 渲染 → PRESENT → `FlushBuffer`。
第一帧 `rects=0`（整块）是对的：那块 buffer 第一次用，按环的规矩必须整帧刷。

**只有 1 帧**这件事本身也是证据：counter 是静态界面，`ui` 画完一帧就不再要了——
如果还是 S1 那种定频循环，这里会是几十帧/秒。

### 还没拿到的：画面

设备锁屏了，而且是**要 PIN 的锁**：`power-shell wakeup` 能把屏幕点亮，
`uinput` 的滑动手势锁屏壁纸会响应（那只柯基会动），但解不开。

也试过把 buffer 落到应用沙箱里再拉出来——`hdc shell` 是 uid 2000(shell)，

    ls /data/storage/el2/100/base/dev.egoist.music → Permission denied

拉不到。所以 S2 的退出判据（屏幕上看见 counter）差最后一步，需要把设备解锁。

顺带记一笔：`ui` 走的是软件路径。`Surface.Native()` 返回零值，
GPU 渲染器造不出来就退回 `raster`，也就是 `framePath = "drawn in memory"`——
这正是 S2 想要的，不用 `MYGO_FRAME_STATS` 也能确定。

## 第十二轮（12:05–12:30）：S3 方案转向 —— 自带 musl Pango 栈，`pango_linux.go` 零修改上屏

### 为什么不写 `OH_Drawing` 了

重写一套 `OH_Drawing` 文字后端意味着维护 ~1500 行平台专有代码（双向文本、CJK 标点选字、断行、自定义字体注册、彩色 Emoji、字形度量与提示），且排版细节必然与桌面端出现差异。
而 OHOS 原生就是 `aarch64-linux-musl` ABI：只要把 `pango_linux.go` 通过 `purego` 加载的 8 个根库及其 `DT_NEEDED` 依赖（共 33 个 musl `.so`）随 HNP 一起打进去，`pango_linux.go` **一行都不用改**。

### 关键细节

1. **依赖闭包与签名**：`tools/hnp` 用 Go 标准库 `debug/elf` 从 `libgobject-2.0.so.0`、`libpango-1.0.so.0`、`libglib-2.0.so.0`、`libpangocairo-1.0.so.0`、`libcairo.so.2`、`libharfbuzz.so.0`、`libpangoft2-1.0.so.0`、`libfontconfig.so.1` 自动递归解析非系统 `DT_NEEDED`（共 33 个 `.so`，未压缩 12.16MB，打进 `.hnp` 后总包仅增加 ~5.2MB）。Harmonybrew 构建的 `.so` 原生自带合法 `.codesign` 且使用 `DT_RUNPATH`，原样拷入 `mygo_<ver>/lib/` 后，`LD_LIBRARY_PATH` 优先级高于 `DT_RUNPATH`，完全自包含。
2. **沙箱内的 HNP 路径解析与环境变量**：HNP 安装后 `/data/app/bin/mygo-engine` 是指向 `../mygo.org/mygo_<ver>/bin/mygo-engine` 的符号链接。`host.cpp` 在 `execve` 前调用 `realpath` 反推出包根 `<pkgRoot>`，在子进程环境注入：
   - `LD_LIBRARY_PATH=<pkgRoot>/lib`（必须在 `execve` 前设置，musl 动态链接器只在启动时读一次）
   - `FONTCONFIG_FILE=<pkgRoot>/etc/fonts/fonts.conf`（扫描 `/system/fonts`，映射 `HarmonyOS Sans` / `HarmonyOS Sans SC` / `Noto Sans Mono` / `HMOS Color Emoji`）
   - `HOME` / `XDG_CACHE_HOME` / `TMPDIR` 指向应用沙箱 `/data/storage/el2/base/haps/entry/{files,cache,temp}`，既让 fontconfig 持久化缓存，也让 `pango_linux.go` 的 `AddFont`（`os.UserCacheDir()`）可写。
3. **首帧看门狗放宽**：首次安装冷启动扫描 `/system/fonts`（263 个字体）建缓存需数秒，首帧 `pending` 超时放宽至 15s，建完缓存后启动即达毫秒级。
